# Content-Security-Policy — 2026-09-09

Fourth item from the security review's roadmap (A04/A05). Builds on
[AUDIT_LOG_2026-09-09.md](AUDIT_LOG_2026-09-09.md). The settings.py comment
this closes has been sitting there since SECURITY*CLEANUP: *"A
Content-Security-Policy is the real replacement [for the dead XSS filter] -
not yet configured, needs a pass to inventory inline styles/scripts first."\_

## Why a policy this strict was even attempted

CSP is normally rolled out permissively (`unsafe-inline` on style-src at
least) because most real apps have some inline styling and nobody wants to
spend a day chasing it down. This app is small enough to just check: a
prior grep for this same security review already found zero
`dangerouslySetInnerHTML`, `innerHTML`, or `eval` calls anywhere in the
frontend. That's the precondition for attempting a fully strict policy
(no `unsafe-inline` at all) instead of settling for a weaker one by default.

## Two surfaces, two policies

Django serves HTML in exactly two places: the admin panel and DRF's
browsable API. Everything else the API returns is JSON. The React SPA is a
**separate deployment** (Cloudflare Pages) and Django's CSP header never
reaches it — it needs its own.

### Backend — `hms/middleware.py`

A hand-rolled `ContentSecurityPolicyMiddleware`, not `django-csp`: the
policy is one static string, and the only thing worth "adding" over a
manual header is nonce generation for inline scripts — moot once the
inventory came back empty. Positioned right after `SecurityMiddleware`, so
it sees every response on the way out, including WhiteNoise's static-file
responses.

```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:;
font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self';
form-action 'self'
```

No `unsafe-inline` anywhere. This was not assumed — it was tested live.

### Frontend — `front/public/_headers`

Cloudflare Pages' convention: a `_headers` file at the deployed root applies
response headers to every request, and Vite copies `public/` into `dist/`
at build time, so this ships automatically. Same strict policy, plus three
headers the static host doesn't apply on its own that Django already sets
for its own pages (`X-Frame-Options: DENY`, `X-Content-Type-Options:
nosniff`) and one new one: `Referrer-Policy: strict-origin-when-cross-origin`
— the literal browser-level mechanism behind this project's own "PII-free
URLs" claim (README: SSN/Medicare never appear in a URL, browser history, or
`Referer` header). CSP alone doesn't guarantee that; a permissive referrer
policy would leak the current URL to any `connect-src`-allowed origin on
cross-origin requests.

**One thing this file can't do:** `connect-src` needs the real deployed API
origin, and a static file can't read `VITE_API_BASE_URL` at request time.
Shipped with a `<API_ORIGIN>` placeholder and a comment — has to be
hand-edited once at deploy time. Fails closed if forgotten (the SPA simply
can't reach the API), not a silent security gap.

## Verification — live, not assumed

Both surfaces were checked in an actual browser, with real console
inspection, not just read for evidence of a probable problem:

**Backend**, against a live `runserver` + real MySQL, logged in as a real
superuser:

| Page                        | What it exercises                                                 | Console violations |
| --------------------------- | ----------------------------------------------------------------- | ------------------ |
| `/admin/login/`             | Base admin styling                                                | None               |
| `/admin/` (dashboard)       | Admin JS (theme toggle, nav)                                      | None               |
| `/admin/auth/user/add/`     | A JS-driven widget (password-auth radio toggle)                   | None               |
| `/api/` and `/api/persons/` | DRF browsable API — syntax highlighting, filter panel, pagination | None               |

Tried `style-src 'self' 'unsafe-inline'` first (the safe default), then
tightened to plain `'self'` and re-ran every page above — still zero
violations, and a zoomed screenshot confirmed the button styling actually
rendered (blue buttons, not a fallback), not just "didn't error." Shipped
the tighter version.

**Frontend**, against the actual `front/dist` production build (already
checked into the repo from a prior build), served locally with the exact
candidate header via a throwaway Python server: the login page rendered
fully — gradient buttons, icons, client-side routing to `/login` — with
zero console messages. API calls to the dev-only backend origin baked into
that build failed (connection refused, expected — different port), which is
a network error, not a CSP violation, and doesn't affect the script-src/
style-src verdict this was checking.

## What's NOT in this pass

**No CSP violation reporting.** `report-uri`/`report-to` isn't configured —
if the policy ever needs loosening because a future component actually
requires inline styles, nothing currently surfaces that automatically; it'd
show up as a silently broken page instead of a report. Worth adding once
Sentry is actually wired in (item 5 on the roadmap) - CSP reports could flow
to the same place.

**`<API_ORIGIN>` is a manual placeholder**, not templated. Documented as a
deploy-time step rather than solved with build tooling, since there's
exactly one place it's needed and automating a single find-replace isn't
worth a build step.
