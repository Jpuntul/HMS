# Declined Roadmap Items — 2026-09-09

Two items from the security review's roadmap, closed by deciding not to
build them rather than by building something. An ADR with only accepted
proposals is marketing — the rejected half of a decision is the part that
evaporates from memory and can't be recovered from the code, so it goes
here in the same format as an accepted one.

---

## ADR: Field-level encryption at rest for SSN/Medicare/telephone/email

**Status:** Declined

**Context:** `SECURITY_CLEANUP_2026-05-24.md` named this as an open
follow-up. `Persons.SSN`, `Medicare`, `Telephone`, and `Email` are stored
as plain columns. The security review scored this Medium (A02).

**Decision:** Not building it, for this project, as deployed.

**Alternatives considered:**

- **Column-level encryption (e.g. `django-cryptography` or hand-rolled
  `Fernet`)** — the literal ask. Rejected: encrypted columns can't be
  indexed the normal way, so `PersonSerializer`'s search on `ssn`/`medicare`
  (`PersonListCreateView.search_fields`) either breaks or needs a second
  deterministic-hash column just to remain searchable — real schema
  surgery on a `managed=False` table, raw DDL, for a threat this
  deployment doesn't have.
- **Application-level encryption only on the most sensitive fields** —
  smaller version of the same idea, same DDL/indexing cost, smaller
  benefit.
- **Do nothing** — chosen.

**Consequences:**

- Zero implementation cost, zero query/index breakage, nothing to get
  wrong.

* SSN/Medicare/etc. remain plaintext at rest. If this system ever
  legitimately held real PHI, this decision would need to be reopened
  first, not last — encryption-at-rest is exactly the kind of control a
  real compliance review would require.
* This is not a gap being missed; it's the same scope boundary the
  architecture document already draws explicitly: _"synthetic data only...
  no BAA, no audited access controls."_ Encrypting columns to protect data
  that was never going to be real doesn't change the actual risk, which is
  entirely about not deploying real PHI here at all — a decision made once,
  upstream of this one, not per-column.

**The honest trigger that would flip this:** the day this system is
scoped to hold real patient data. Not before.

## ADR: Multi-factor authentication

**Status:** Declined

**Context:** The security review listed MFA as the lowest-priority item
(A07) after RBAC, audit logging, CSP, dependency pinning, and access-token
tuning were all addressed this week. Discussed directly rather than
defaulted past.

**Decision:** Not building it.

**Alternatives considered:**

- **TOTP via `django-otp`** — the standard self-hosted approach, no
  recurring cost. Rejected on fit, not cost: see Context below.
- **SMS-based OTP** — rejected outright; recurring per-message cost on a
  $0 budget, and SMS OTP is the weaker MFA method regardless (SIM-swap
  risk) — would have been the wrong choice even at a real company.
- **Do nothing** — chosen.

**Consequences:**

- Zero implementation cost, zero added login friction for the 3 real
  accounts.
- The threat MFA specifically defends against — an attacker who already
  has a valid username+password (leaked-password reuse, a keylogger,
  shoulder-surfing) — is real but narrow at 3 admin-provisioned accounts
  with no public signup surface. Compare to what already shipped this
  week and covers more ground for the actual threat model: login is
  throttled (brute force), `register_view` now validates password
  strength (weak passwords rejected at creation), and refresh tokens are
  blacklisted on rotation (a stolen one is usable exactly once). MFA would
  be one more layer on top of an already-narrow remaining gap.

* If a stolen/reused password is ever the actual vector, MFA would have
  stopped it and nothing currently in place does. That's the real,
  accepted risk being carried.
* **The reasoning is the deliverable here, not silence.** This project's
  own `SYSTEM_DESIGN_METHOD.md` makes the identical argument about
  infrastructure in general: _"knowing you are not at scale — and being
  able to show the arithmetic that proves it — is a more senior signal
  than reciting the components of a system that is."_ Same shape of
  argument, applied to a security control instead of a scaling one.

**The honest trigger that would flip this:** the account count or the
threat model changing — more staff, external-facing accounts, or any
signal that credential reuse/leakage is an actual observed pattern rather
than a theoretical one.
