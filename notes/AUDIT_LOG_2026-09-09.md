# Audit Logging — 2026-09-09

Third item from the security review's roadmap (A09, Security Logging &
Monitoring Failures — High). Builds on
[RBAC_STAFF_WRITE_GATE_2026-09-09.md](RBAC_STAFF_WRITE_GATE_2026-09-09.md).

## Why

Soft delete answers "is this row recoverable?" — it has never answered "who
changed it, and when?" On tables holding PHI-shaped data, that's a real gap:
until this pass, nothing recorded who deleted a patient's infection record
or edited a facility's capacity. The architecture and security review
documents both named this as an open tradeoff rather than a bug.

## Scope decision

Three options were on the table: log lines only (cheapest, not queryable
in-app), a custom DB-backed table (chosen), or `django-simple-history`
(most complete, but its per-model historical tables aren't built around
composite primary keys — and this codebase's composite-PK handling has
already produced one real bug, per `DB_SCHEMA.md` §4.5). Went custom to
avoid integration risk with `Infection`/`Vaccination`/`Employment`/
`Schedule` for a feature that only needs to answer "who/what/when," not
produce field-level diffs.

## What changed

**`hms/models.py` — `AuditLogEntry` (new).** The one `managed=True` model in
this file — everything else there is `managed=False` by the project's
central invariant; this is a new table and is Django's to create and alter
normally. Fields: `actor` (FK to `auth.User`, `SET_NULL` so a deleted user
account doesn't cascade-delete its own history), `action`
(create/update/delete), `model_name`, `object_pk`, `object_repr` (a
point-in-time `str()` snapshot — the record itself may be edited or hard-
deleted later, so this is the only place its identity survives), and
`timestamp`. `object_pk` is a `CharField`, not a real foreign key —
composite-PK models don't have one scalar value to reference, so this
stores `str(instance.pk)` uniformly. Verified: for a `CompositePrimaryKey`
model this renders as `(202078693, 1, datetime.date(2003, 12, 12))` — a
readable tuple, well inside the 255-char column.

**`back/hms/migrations/0003_auditlogentry.py` — hand-written, not
`makemigrations`-generated.** Running a bare `makemigrations hms` swept in
every domain model (`Employee`, `Facility`, `Infection`, ...) alongside
`AuditLogEntry`, because they've never had migration state recorded — the
project's established pattern (only `Person` was ever tracked, in
`0001`/`0002`; everything since was added to `models.py` directly, per
CLAUDE.md's "never run makemigrations for domain models"). Deleted the
generated file and wrote one containing only `AuditLogEntry`'s `CreateModel`

- its two indexes. Confirmed via `git stash` that the domain-model drift
  `makemigrations --check` still reports is pre-existing and unrelated to
  this change — present with this work stashed out entirely.

**`hms/views.py` — `AuditLogMixin`.** Hooks DRF's `perform_create` /
`perform_update` / `perform_destroy`, not `Model.save()`/`.delete()` — stays
out of `models.py`, and only fires for the API write path (the only write
path that exists for these models today). Logs _after_ the underlying
operation succeeds, never before, so a failed write can't produce a false
log entry. `perform_destroy` captures the model name / pk / repr _before_
calling `super()`, since a hard delete leaves nothing to introspect
afterward and even a soft delete mutates the instance in place. Added to
all 20 generic CRUD view classes (10 list/create + 10 detail) via one
mechanical edit — every `generics.` occurrence in `views.py` is a CRUD view
that should get it, confirmed by grep before applying.

## What's NOT in this pass

**Nothing reads the log back yet.** No admin registration, no API endpoint,
no UI page. `AuditLogEntry.objects` is queryable via `manage.py shell` today
only. Scoped out deliberately — the review's finding was "nothing records
who changed what," which this closes; "give staff a way to view it" is a
separate, smaller follow-up once this has real data in it.

**No field-level diffs.** One row per write, not a before/after snapshot of
every field. Matches the `django-simple-history` tradeoff discussion —
that's the heavier feature this pass explicitly avoided.

**Analytics/read-only endpoints are untouched.** `AuditLogMixin` only
attaches to views that support create/update/delete; the function-based
`@api_view` analytics endpoints in `analytics.py` never call `perform_*`
and were left alone.
